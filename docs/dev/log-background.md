# libnvfair 日志系统背景知识(前置阅读)

> 状态:v0.1(2026-11-12)
> 定位:与 hook-background.md 同系列,PBI-002 日志部分的共性背景,回答三个高频问题:
> ① 写文件/输出方式的差别(缓冲区、直写、原子性边界);
> ② `std::memory_order_relaxed` 等内存序参数怎么理解、为什么日志级别选 relaxed;
> ③ 上述选择对 LD_PRELOAD 库和热路径(BR6)意味着什么。
> 事实源:src/util/log/log.cpp 现状、C 标准与 POSIX write(2) 语义、C++11 内存模型。

## 1. 几种"写文件/输出"方式的差别

### 1.1 全景:数据从进程到目的地经过几层

| 方式 | 经过层 | 缓冲 | 原子性 | 典型用途 | 风险点 |
|---|---|---|---|---|---|
| `printf` / `cout` | stdio 缓冲 → `write` | **有**(全缓冲;终端上 stdout 是行缓冲) | 单次 write 内原子 | 普通程序输出 | 多线程交错;LD_PRELOAD 里不安全 |
| `fprintf(stderr,...)` | stderr 特例:默认**无缓冲**,每次直接落盘 | 无(stderr 默认) | 同上 | 调试输出 | 仍走 stdio 内部锁 + 可能 malloc |
| `::write(fd, ...)` | **直写内核** | 无 | ≤PIPE_BUF(4096) 的单条写对管道/O_APPEND 文件原子 | 日志、IPC | 可能部分写,需接受或循环补写 |
| `fwrite(fp)` | stdio 缓冲 → write | 有 | 同 stdio | 二进制大块 | 与 read/fread 混用要 fflush |
| `mmap` + 内存写 | 页缓存,无 syscall | 由内核页缓存管理 | 无单条写原子性 | 高频共享数据(PBI-006 账本) | 同步靠 msync/mmap 语义 |

### 1.2 "缓冲"与"直写"的本质区别

stdio(`printf`/`fwrite`)在**用户态**维护一块缓冲区,攒够才调一次 `write`:
- 优点:系统调用少、吞吐高;
- 缺点:实时性差(崩溃时缓冲区内容丢失)、多线程下日志行互相拼混。

直写(`::write`)每次一个系统调用,实时性最好,每条消息独立。

### 1.3 stderr 的特殊性

C 标准规定 **stderr 默认无缓冲**——它要承载"崩溃前的遗言",不能被缓冲吞掉。
所以 `fprintf(stderr, ...)` 实际每次都等价于"printf + fflush",这也是它比 stdout 慢的原因。

### 1.4 原子性的准确含义(边界要记牢)

- 对**普通文件**,`write` 不保证原子(可能部分写);
- 对**管道 / O_APPEND 打开的文件**,≤PIPE_BUF(Linux 上 4096)的单次 write 保证
  与其他进程/线程的写**不交错**(要么整体进,要么整体不进);
- 当前 log_write 单条 ≤4160 字节,**略超 PIPE_BUF**,极端情况下跨线程交错仍可能发生。
  要绝对原子需压到 4096 内或加锁;对诊断日志够用,知道边界在哪即可。

### 1.5 为什么 libnvfair 的日志选 write 而不是 fprintf(stderr)

三个理由,都源于 LD_PRELOAD 库的特殊处境:

1. **绕开 stdio 的锁与内部 malloc**:宿主进程可能正持有 malloc 锁、正处崩溃边缘,
   此时日志函数再去 malloc 会二次故障;`write` 不经过 stdio,无此依赖。
2. **一条日志 = 一次系统调用**:语义最直白,不依赖 stdio 缓冲策略。
3. **stdout/stderr 分流是硬要求**:宿主 stdout 可能被上层脚本解析(nvidia-smi 数值、
   容器 runtime 抓状态),日志只能进 stderr——重定向时两条管道可分离
   (`app > out.txt` 后 stderr 仍打屏),平时混在同一屏幕只是默认行为。

## 2. std::memory_order_relaxed 等内存序

### 2.1 先分清两层保证

`std::atomic<T>` 保证**单次读改写不可分割**(不会读到写一半的值)——这是基础,
与 memory_order 无关。**memory_order 管的是另一件事:操作前后的可见性顺序**。

### 2.2 三级速查

| order | 保证 | 代价 | 适用 |
|---|---|---|---|
| `relaxed` | 只保证原子性,不约束与其它内存操作的顺序/可见性 | 最便宜(x86 上就是普通 mov) | 计数器、日志级别这类"迟到无妨"的标志 |
| `acquire`/`release` | release 写**之前的所有写**,对 acquire 读之后的操作可见 | 中 | 发布数据:写方备好数据后置标志,读方见标志即数据就绪 |
| `seq_cst`(默认) | 全局唯一顺序,所有线程看法一致 | 最贵 | 需要严格一致的场景 |

### 2.2 log.cpp 为什么选 relaxed 是正确而非偷懒

log_level 被保护的**只有级别这一个值**,没有伴随数据需要靠它同步。
级别晚一小拍生效的后果:某线程刚设 Debug,另一线程下一次 log_write 仍按旧级别
过滤——仅仅是少打/多打一条日志,下一刻自愈。**容忍度恰好等于 relaxed 提供的保证**。

对比:PBI-004 账本的"已用量"字段不能 relaxed 随便读——它周围伴随真正的共享数据
(句柄表、配额),要用 acquire/release 保证"看到新用量时,必然也看到与这笔账
关联的所有写入"。

### 2.3 选型口诀

> 值本身独立、晚点无妨 → relaxed;
> 一个标志保护一批数据 → acquire/release;
> 全局单一时间线 → seq_cst。

选 relaxed 唯一要回答的问题:**这条标志迟到生效,会不会让程序状态错掉?**
日志级别显然不会。

### 2.4 成本账

x86 上 relaxed 与 seq_cst 的 load/store 编出的指令往往相同(x86 内存模型天然强),
差别在**编译器重排序自由度**与跨架构(ARM/POWER 上 relaxed 明显更快)。
选 relaxed 给了编译器和 CPU 全部优化空间——这正是热路径(BR6:拦截路径不阻塞、
不分配)要的东西。
